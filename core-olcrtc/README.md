## Что чинит

Апстримный `datachannel` через носитель WbStream не собирает пару вообще: сервер логирует
`session opened`, клиент падает по таймауту либо на `CONTROL_PING`. На vp8channel та же пара
собирается за секунду.

**Корень (замерено, не гипотеза):** участник LiveKit начинает получать data-пакеты не сразу
после входа в комнату. Сервер отвечает мгновенно, и `SERVER_WELCOME` улетает в пустоту.
Хронология: приветствие 137 байт в 13:52:59 клиент не получил, пакеты 52 и 128 байт
в 13:53:09 и 13:53:19 получил все до единого.

## Что в патче

| Правка | Файл | Зачем |
|---|---|---|
| Ждём первый пакет от пира перед `CLIENT_HELLO` | `internal/client/client.go` | **главная.** Первый входящий пакет = доказательство, что наша подписка активна и ответ будет кому принять. Сервер шлёт keepalive раз в 10 с, он и разблокирует. Потолок ожидания 20 с, превышение не фатально (идём дальше, решает обычный дедлайн) |
| `RequireTargetedPeer` только для транспортов с эпохами | `internal/client/client.go` | у datachannel нет эпох, у движка livekit нет адресной отправки (`SendTo` отсутствует), поэтому ответ всегда широковещательный, а клиент такие молча выбрасывал |
| Пропуск залётных `CONTROL_*` фреймов | `internal/handshake/handshake.go` | у серверной стороны эта защита уже есть (`server.acceptHandshake`, `maxStaleRetries`), у клиентской не было |

Прогрев включается **только** для транспортов без эпох (`isBroadcastOnlyTransport`), поэтому
vp8channel идёт как в апстриме, без лишних задержек. `DefaultTimeout` оставлен апстримный (15 с).

## Как собрать

```bash
git clone --depth 1 https://github.com/openlibrecommunity/olcrtc.git src
python3 /path/to/core-olcrtc/apply.py src
docker run --rm -v /opt/olcbuild:/out -w /out/src golang:1.26.3 bash -c \
  'CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o /out/olcrtc.final ./cmd/olcrtc'
```

Для `.aar`: gomobile с `-checklinkname=0` (см. `magefile.go`, цель `Mobile`).

## Своя control-плоскость для datachannel (07.08.2026)

**Что чинит.** Связь рвалась под нагрузкой: ядро считает канал мёртвым после N промахов
служебного пинга, а пинг под качкой опаздывал. Замер прибором (`debug: true` у клиента,
строки `control alive ... rtt=`):

| нагрузка | ответ на пинг |
|---|---|
| покой | 44 мс |
| 4 потока по 20 МБ | 1-10 с, пик 9.7 с |

**Причина.** `transport.ControlPlane` реализует **только vp8channel**. У datachannel её нет,
поэтому пинг едет одним потоком smux вместе с данными и стоит в очереди за мегабайтами.
Отсюда же и то, что на боевом стенде с olcbox (vp8channel) держалось часами.

**Как сделано.** У LiveKit в пакете данных есть `topic`: control уходит своим topic'ом
(`olcrtc-ctl`) мимо очереди отправки движка, на приёме разводится по topic до расшифровки.
Реализованы `engine.ControlSession` (livekit) и `transport.ControlPlane` (datachannel).

**Чего это НЕ чинит.** Труба у LiveKit одна надёжная, поэтому очередь никуда не делась:
под экстремальной нагрузкой пинг всё ещё ждёт 2-9 с. Обрывов нет только потому, что пороги
живости выровнены на обеих сторонах (10 с интервал, 30 с ответ, 6 промахов ≈ 3 минуты).
Полное лечение — вынести пинги из smux на ненадёжную трубу, где очереди нет; просто
перевести туда весь control нельзя, smux не переживает потерю фрейма.

**Что пробовали и откатили.** Обратное давление (очередь отправки 5000 → 256 плюс ожидание
места вместо отказа) сделало хуже: скорость 21.6 → 11.4 Мбит/с и шесть обрывов вместо нуля.

**Версии должны совпадать на обеих сторонах.** Нога слушает control своим каналом, поэтому
телефон со старым ядром с новой ногой не договорится (и наоборот): данные идут, пинги нет,
разрыв через полторы минуты. Бинарь ноги теперь собирается тем же прогоном CI
(`build-olcrtc.yml`, артефакт `olcrtc-linux-amd64`) — ставить парой с релизом APK.
